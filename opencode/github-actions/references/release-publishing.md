# Release lifecycle for an OCI-backed action catalog

## Event policy

Keep these choices explicit rather than treating them as GitHub constraints:

- Branch `push`: selected development checks/builds.
- `workflow_dispatch`: explicitly route release preparation, maintenance and runner
  qualification modes. Enforce main-only release preparation; reject conflicting
  modes or define their precedence. Maintenance/qualification requests must not
  accidentally enter publication. Manual dispatch can target other references.
- SemVer tag `push`: catalog release verification and GitHub Release publication.
- `schedule`: Renovate, vulnerability rescans and external-link checks only.
- No PR trigger by default for this user's repositories. A merge push still runs
  development checks, and direct pushes to main stay allowed.

Tag filters are globs. Validate the actual SemVer and whether pre-releases are
allowed. A Git tag points at a commit, not "a branch"; verify its commit is reachable
from main according to the chosen release policy. Keep version derivation explicit
instead of inferring artifact identity from a mutable tag or a working directory.

## The image-reference ordering constraint

An action released with a digest reference must point at an already published image.
For this catalog, prepare in this order:

1. Capture the intended main commit and previous release. Determine the next version
   using git-cliff/Conventional Commits and an explicit bump policy. Handle first
   release and no-bump cases without inventing an initial version.
2. Build changed candidate images from that source in `build`, then transfer the
   untested archives/receipts to `test`. Verify the checksums and native Docker
   action interfaces, generate Syft SBOMs and Grype reports, and mark qualification
   only after success. Do not reconstruct the images in the test phase.
3. Publish those outputs, capture remote digests, and sign/attest/verify them.
4. Aggregate results in one writer. Update action digest references and notes;
   preserve unchanged image references. Confirm required images are accessible.
5. Check main has not advanced and the tag does not exist. Commit reference updates
   and notes, then atomically push the final commit and new tag. Serialize this
   publication, reject races and never force-push or move an existing release tag.
6. On tag push, verify references/signatures and publish GitHub Release notes/assets.
   Do not rebuild images just because the catalog received a tag.

Image source commit and final catalog commit can differ because the final commit
records published digests. Record both roles explicitly; do not pretend the image
was built from the later reference-update commit.

Manual tags must reference a valid catalog with existing images; fail clearly when
they do not. Never move a release tag silently to repair it. Global catalog versions
do not require rebuilding every image: unchanged digests remain pinned independently
of the catalog version. Reserve catalog SemVer for Git tags/GitHub Releases and
publish images by digest. Technical Cosign signature tags required by a registry
are not catalog-version aliases.

Keep planning, exact-source validation, publication, signing, verification,
finalization and GitHub Release creation as explicit `uses:` steps backed by
specialized Docker actions. A host Python publisher or `gh`/engine shell block is
not the completed architecture. Official token/artifact actions remain explicit
infrastructure exceptions. Remove migration-only bridges after publication and
validate the newly activated release path on GitHub.

Treat action metadata and its pinned executable as a versioned interface. Publish
and qualify support for new inputs/outputs before workflow callers depend on them;
editing action.yml does not update the executable behind its existing digest.
Verify both the new output producer and its downstream consumers during activation.

## Trigger authentication and races

Events generated by a workflow using the repository's normal `GITHUB_TOKEN`
generally do not trigger further workflow runs; explicit `workflow_dispatch` and
`repository_dispatch` are documented exceptions. For preparation → tag push → release,
use an appropriately scoped GitHub App installation token or another explicitly
chosen mechanism. Do not claim an ordinary GITHUB_TOKEN tag push will run release CI.

Check source-push credentials before remote work: an OAuth token pushing changes
under `.github/workflows/` needs the appropriate `workflow` scope in addition to
repository access. For other token types, verify their applicable repository and
workflow permissions instead of assuming OAuth scope names apply. Keep this identity
distinct from the job's GITHUB_TOKEN, release App and Renovate bot. Request missing
access or a user-performed push without displaying tokens or bypassing restrictions.

Keep the App/token narrowly scoped and separate from OCI signing identity. Avoid
recursive release preparation from generated commits. Serialize release preparation
and publication, without cancelling a release mid-push. Development cancellation
can be per branch, but must not accidentally cancel preparation/release runs sharing
a concurrency group. Keep the captured-commit comparison even with concurrency:
direct main pushes can occur outside the release workflow.

On retry, inspect existing remote tags, manifests and release records. Reuse only
outputs proven to belong to the intended source/version. Fail on conflicting
immutable identities; do not overwrite a published version to make a rerun pass.
Document orphaned images from partial preparations and retention/cleanup policy.

## SBOM, scanning and signing

Generate SBOMs with Syft; retain existing producer/Yocto SBOMs when they add build
dependency information. Scan with Grype using a documented database freshness
policy and the `high` severity gate. Do not lower the gate or add broad exclusions
to pass CI. Advisory reviews must fail closed when required symbols or exact
patched-file evidence are absent, ambiguous or altered. Keep the reports even on scan failures without masking
the failing outcome. Maintenance can rescan published SBOMs/images as vulnerability
data changes, without rebuilding them.

Sign remote image digests with Cosign. For keyless GitHub signing, the signing job
requires `id-token: write`; grant registry permissions separately. A composite or
container cannot grant itself permissions. Validate OIDC forwarding/token acquisition
and registry authentication for the exact containerized invocation. Do not expose
tokens in argv/logs. Verify expected certificate identity and issuer, not merely the
presence of any signature. Distinguish image signatures from SBOM attestations.

Use Grype, not Trivy, for this user's workflow. Configure Renovate for upstream tool
pins, image base digests and action references. Signed/released images, generated
SBOMs and CI reports are different artifacts with distinct retention needs.

## Native maintenance

Compose maintenance from Docker actions for catalogue SBOMs, reviewed vulnerability
scans, link checks and Renovate. Refresh the vulnerability database explicitly and
retain its metadata; do not rebuild images merely to rescan them. Keep internal
signing configuration, database caches and credentials out of report artifacts.

Use a dedicated Renovate bot/App token with the required repository, pull-request
and workflow-update permissions. Confirm the hosted Renovate App is disabled before
enabling the containerized runner, and do not reuse release credentials implicitly.
Distinguish a wired but disabled step from a live, authenticated maintenance run.
Inventory dependency managers and file patterns against actual sources: include
npm lockfiles when present, Go modules/tool pins across all relevant action families,
base images and external action references. Do not assume enabling a manager proves
it detected every dependency; inspect extraction results.

Validate configuration first, then run an authenticated full dry-run and inspect
resolved dependencies before enabling PR creation. A valid config or the presence
of a secret does not prove authentication or write permissions. Check permissions
for Contents, pull requests, workflow updates and Issues when the dependency
dashboard is enabled; distinguish PAT scopes from App/fine-grained permissions.
Generate short-lived App tokens per execution when that credential type is chosen.

Document manual versus scheduled behavior, dry-run defaults and actual trigger
times in the repository. Confirm observed step execution and its result, not merely
a successful workflow containing a skipped Renovate step. Do not add an unrequested
enable variable or approval gate; make existing event and mode routing explicit.

Retire one-off shared-package deletion and bootstrap steps once their migration is
complete; do not leave destructive historical controls as routine maintenance.

## Evidence and external setup

List runner labels/capacity, GHCR access, package visibility, App installation and
permissions, signing identity, and release-policy inputs that actually require
setup. Do not fabricate configured secrets or claim a remote workflow ran because
its YAML passed validation. Record commands, report paths and published digests
only when observed.
